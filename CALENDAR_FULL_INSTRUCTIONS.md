## 2. Цель продукта

Приложение предназначено для владельца школы, администратора и в дальнейшем учителей. Оно должно объединять:

- календарь занятий;

## 6. Авторизация и роли

Использовать Firebase Authentication Email/Password и профиль `users/{uid}`.

Базовая модель профиля:

```ts
type UserRole = "owner" | "admin" | "teacher" | "parent";

interface UserProfile {
  name: string;
  email: string;
  role: UserRole;
  schoolId: string;
}
```

Пока основной интерфейс календаря доступен владельцу и администратору:

- `owner` — полный доступ ко всем данным школы, включая оплаты;
- `admin` — полный операционный доступ к календарю и оплатам;
- `teacher` — архитектурно предусмотрен, доступ к оплатам запрещён;
- `parent` — архитектурно предусмотрен, доступ к оплатам запрещён.

Для обратной совместимости существующий главный пользователь с ролью `admin` продолжает иметь полный доступ. Не блокировать рабочий аккаунт при добавлении роли `owner`.

Учитель получает только документы `groups` и `lessons`, где `teacherId` равен его Firebase Auth UID. Администратор закрепляет учителя за группой. Учитель не видит оплаты, не создаёт и не удаляет группы или уроки, но может открыть свой урок, отметить посещение и домашнюю работу детей и написать общее домашнее задание группе.

Пока Firebase проверяет пользователя, показывать loading screen. Если профиль отсутствует либо неполный, показывать понятное сообщение. После выхода направлять на страницу входа.

## 7. Изоляция данных школы

Каждая основная сущность содержит:

```ts
schoolId: string;
```

Все запросы Firestore должны получать только документы текущей школы:

```ts
query(collection(db, "..."), where("schoolId", "==", userProfile.schoolId))
```

Не загружать документы других школ и не полагаться только на фильтрацию в интерфейсе. Firestore Security Rules также должны ограничивать доступ по `schoolId` и роли.

## 8. Участники занятий

Поддерживать три взаимоисключающих формата:

1. `individual` — индивидуальное занятие;
2. `pair` — пара;
3. `group` — группа.

В интерфейсе формы занятия показывать три отдельные строки с радиовыбором:

```text
○ Индивидуал
○ Пара
○ Группа
```

Одновременно можно выбрать только один вариант. После выбора отображать соответствующий список участников.

Модель:

```ts
type GroupKind = "individual" | "pair" | "group";

interface Group {
  id: string;
  schoolId: string;
  teacherId?: string;
  kind: GroupKind;
  name: string;
  color: string;
  course?: string;
  level?: string;
  studentIds: string[];
  notes?: string;
  monthlyLessonTarget: number;
  createdAt: Timestamp;
  updatedAt: Timestamp;
}
```

Старые документы без `kind` считать группами. Для старых документов без `monthlyLessonTarget` интерфейс должен предложить выбрать значение, но не падать.

В левой панели показывать всех участников и их тип. Разрешить создание, фильтрацию и удаление после подтверждения. Удаление участника не должно автоматически удалять исторические уроки и финансовые записи.

## 9. План количества уроков в месяц

Для каждого индивидуального ученика, пары или группы обязательно предусмотреть поле:

```text
Количество уроков в месяц
```

Разрешённые значения:

```text
6, 7, 8, 9 или 10
```

Предпочтительный интерфейс — select или компактный stepper с минимальным значением 6 и максимальным 10. Нельзя сохранить 5, 11, дробное значение или пустое значение.

Значение хранить в документе участника:

```ts
monthlyLessonTarget: 6 | 7 | 8 | 9 | 10;
```

План применяется отдельно к каждому календарному месяцу. При просмотре месяца показывать:

```text
План: 8 уроков
Запланировано: 7
Проведено: 5
Осталось: 3
```

Правила подсчёта:

- период всегда начинается в 00:00 первого числа выбранного месяца;
- период заканчивается в 23:59:59 последнего календарного дня этого же месяца;
- урок относится к месяцу по локальной дате школы;
- одно вхождение повторяющейся серии считается одним уроком;
- исключённое/удалённое вхождение не считается;
- перенесённый урок считается в месяце своей фактической даты;
- количество дней месяца определять календарно, без фиксированного значения 30 или 31;
- при смене месяца показатели пересчитываются автоматически.

План можно изменить для будущих месяцев. Изменение плана не должно изменять уже сохранённые оплаты прошлых месяцев.

## 11. Повторяющиеся занятия

Пользователь может включить «Повторять занятие», выбрать один или несколько дней недели и дату окончания.

Использовать ISO-дни недели:

```text
1 — понедельник
2 — вторник
3 — среда
4 — четверг
5 — пятница
6 — суббота
7 — воскресенье
```

Не сохранять каждое повторение отдельным документом. Один документ урока является шаблоном серии. Вхождения генерировать для отображаемого периода.

При удалении повторяющегося занятия предлагать:

- «Только это занятие» — добавить дату в `excludedDates`, не удаляя шаблон;
- «Всю серию» — удалить документ шаблона полностью.

При удалении одиночного урока показывать обычное подтверждение.

## 12. Журнал посещаемости и домашней работы

Для группы отображать список детей с ФИ.

Для каждого ребёнка на конкретной дате урока хранить:

```ts
interface StudentLessonStatus {
  attended: boolean;
  homeworkDone: boolean;
}
```

Визуальные состояния:

- посещение зелёное — «Был(а)»;
- посещение красное — «Не был(а)»;
- домашняя работа зелёная — «Была»;
- домашняя работа красная — «Не была».

У повторяющейся серии статусы хранятся отдельно для каждой даты. Изменение журнала одного урока не меняет другие даты серии.

В месяце показывать всю календарную сетку. В режимах дня и недели показывать временную шкалу. Поддерживать создание кликом по дате, редактирование карточки, drag-and-drop и изменение длительности одиночного урока.

Для повторяющихся уроков нельзя молча применять drag-and-drop ко всей серии. До реализации выбора области изменения повторяющиеся карточки могут быть заблокированы для drag-and-drop и редактироваться через форму.

## 15. Модуль оплат

### 15.1. Назначение

Модуль является журналом оплат. Он не принимает банковские платежи и не хранит данные карт.

Оплаты видны только:

- владельцу школы (`owner`);
- администратору (`admin`).

Учитель и родитель не должны получать финансовые документы из Firestore даже если вручную откроют URL раздела.

### 15.2. Расчётный период

Каждая оплата относится к одному календарному месяцу:

```text
с 1-го числа месяца до последнего числа того же месяца включительно
```

Хранить месяц в нормализованном виде:

```text
YYYY-MM
```

Например:

```text
2026-08
```

Не использовать скользящие периоды, например с 15-го по 15-е. Не переносить остаток автоматически в другой месяц без явной записи корректировки.

### 15.3. Модель оплаты

Создать коллекцию Firestore:

```text
payments
```

Модель:

```ts
type PaymentStatus = "unpaid" | "partial" | "paid";

interface Payment {
  id: string;
  schoolId: string;
  participantId: string;
  participantNameSnapshot: string;
  participantKind: "individual" | "pair" | "group";
  month: string; // YYYY-MM
  periodStart: string; // YYYY-MM-01
  periodEnd: string; // фактический последний день месяца
  plannedLessons: number; // 6–10
  scheduledLessons: number;
  completedLessons: number;
  amountDue: number;
  amountPaid: number;
  currency: "RUB";
  status: PaymentStatus;
  paidAt?: Timestamp;
  paymentMethod?: "cash" | "transfer" | "other";
  notes?: string;
  createdBy: string;
  updatedBy: string;
  createdAt: Timestamp;
  updatedAt: Timestamp;
}
```

Сумму не вычислять, пока для участника не настроены тарифы. Не придумывать стоимость урока и не подставлять фиктивные значения.

Актуальное правило автоматического расчёта: для каждого ученика, пары или группы хранятся две цены — льготная цена урока по абонементу и цена разового урока. В каждом уроке выбирается `billingType: "subscription" | "single"`. Счёт выбранного месяца рассчитывается автоматически только по реально отображаемым вхождениям календаря:

```ts
amountDue = subscriptionLessons * subscriptionLessonPrice
  + singleLessons * singleLessonPrice;
```

Повторяющиеся занятия по выбранным дням недели по умолчанию относятся к абонементу. Одиночный урок по умолчанию считается разовым, но пользователь может изменить тип оплаты в форме. Исключённое из серии занятие в счёт не входит.

Статус вычислять и отображать так:

- `unpaid` — `amountPaid === 0`;
- `partial` — `0 < amountPaid < amountDue`;
- `paid` — `amountPaid >= amountDue`.

Если `amountDue === 0`, статус задаётся пользователем явно или показывается как «Сумма не указана», а не как автоматически оплачено.

### 15.4. Уникальность

Для одного участника должен быть один основной документ оплаты на месяц.

Рекомендуемый ID:

```text
{schoolId}_{participantId}_{YYYY-MM}
```

Это предотвращает случайное создание дубликатов. При сохранении использовать `setDoc` с контролируемым ID или транзакцию.

### 15.5. Интерфейс оплат

Добавить в левую панель пункт:

```text
Оплаты
```

Страница содержит:

- переключение месяца стрелками;
- кнопку «Текущий месяц»;
- подпись периода, например `1–31 августа 2026`;
- поиск по участнику;
- фильтр `Все / Не оплачено / Частично / Оплачено`;
- итоговые карточки;
- таблицу оплат.

Строка таблицы:

```text
Ученик/пара/группа | План уроков | Запланировано | Проведено | К оплате | Оплачено | Статус | Действия
```

Цвета статусов:

- красный — не оплачено;
- жёлтый или нейтральный фиолетовый — частично;
- зелёный — оплачено.

Цвет не должен быть единственным обозначением: рядом всегда показывать текст статуса.

Действия:

- указать сумму к оплате;
- внести полученную сумму;
- отметить полностью оплаченным;
- вернуть статус «не оплачено» после подтверждения;
- указать способ оплаты;
- добавить заметку;
- посмотреть историю изменений.

### 15.6. Итоги месяца

Показывать:

```text
Начислено
Получено
Осталось получить
Оплачено полностью
Есть задолженность
```

Формулы:

```ts
totalDue = sum(amountDue)
totalPaid = sum(amountPaid)
totalOutstanding = max(totalDue - totalPaid, 0)
```

Все суммы показывать в рублях с форматированием `Intl.NumberFormat("ru-RU", { style: "currency", currency: "RUB" })`.

### 15.7. Реальное время

Использовать `onSnapshot` и запрос только по школе и выбранному месяцу:

```ts
query(
  collection(db, "payments"),
  where("schoolId", "==", userProfile.schoolId),
  where("month", "==", selectedMonth)
)
```

Если Firestore запрос требует составной индекс, добавить ссылку/инструкцию для создания индекса и не заменять запрос загрузкой всех оплат.

### 15.8. История изменений

Финансовые изменения должны быть прослеживаемыми. Предпочтительно хранить журнал в подколлекции:

```text
payments/{paymentId}/history/{entryId}
```

Запись истории:

```ts
interface PaymentHistoryEntry {
  action: "created" | "amount_changed" | "payment_added" | "status_changed" | "note_changed";
  previous?: Record<string, unknown>;
  next?: Record<string, unknown>;
  changedBy: string;
  changedAt: Timestamp;
}
```

Не удалять финансовую историю при обычном редактировании.

## 16. Firestore Security Rules для оплат

Правила должны проверять одновременно:

- пользователь авторизован;
- профиль `users/{uid}` существует;
- `schoolId` документа совпадает со школой пользователя;
- роль пользователя — `owner` или `admin`.

Концептуально:

```text
read/write payments only if
request.auth != null
and user.schoolId == resource/request.resource.data.schoolId
and user.role in ["owner", "admin"]
```

Правила необходимо корректно разделить для `read`, `create`, `update`, `delete`, потому что при создании ещё нет `resource.data`, а при обновлении нужно проверять и старый, и новый `schoolId`.

Запретить изменение `schoolId` существующей оплаты на другую школу.

## 17. Ошибки и состояния интерфейса

Обработать:

- неправильный email или пароль;
- отсутствующий профиль;
- неполный профиль;
- permission denied;
- network unavailable;
- отсутствие групп/учеников;
- отсутствие уроков в месяце;
- отсутствие оплат;
- некорректную сумму;
- план уроков вне диапазона 6–10;
- повторное создание оплаты за тот же месяц.

Пока загружаются данные, показывать skeleton или понятный loading state. Не показывать пустой экран.

## 18. Обязательные тесты

Сохранить существующие тесты и добавить:

- план принимает только целые значения от 6 до 10;
- первый и последний день месяца вычисляются правильно для 28, 29, 30 и 31 дня;
- уроки считаются только в выбранном календарном месяце;
- исключение повторяющегося урока уменьшает количество запланированных уроков;
- удаление всей серии убирает все её вхождения;
- статусы посещения разных дат серии независимы;
- оплату видят `owner` и `admin`;
- `teacher` и `parent` не видят и не запрашивают оплаты;
- `unpaid`, `partial`, `paid` вычисляются корректно;
- остаток не становится отрицательным;
- невозможно создать два основных платежа одному участнику за один месяц;
- запрос оплат ограничен `schoolId` и `month`;
- production-сборка проходит с GitHub Secrets.

## 19. Критерии приёмки

Функция считается готовой, когда:

- владелец и администратор видят раздел оплат;
- учитель и родитель не видят раздел и не могут прочитать данные напрямую;
- период всегда равен календарному месяцу с 1-го до последнего числа;
- для каждого участника можно выбрать план от 6 до 10 уроков;
- видно план, запланированные и проведённые уроки;
- можно указать сумму к оплате и полученную сумму;
- статус оплаты отображается текстом и цветом;
- итоги месяца считаются корректно;
- прошлые месяцы можно просматривать стрелками;
- данные фильтруются по `schoolId` и месяцу;
- изменения синхронизируются через `onSnapshot`;
- Firestore Rules защищают финансовые данные;
- существующий календарь, повторения, журнал группы и дизайн не сломаны;
- `npm run test` и `npm run build` проходят;
- GitHub Pages deployment проходит успешно.

## 21. Запрещённые решения

- Не хранить оплаты в `localStorage`.
- Не загружать оплаты всех школ.
- Не показывать финансовые данные ролям `teacher` и `parent`.
- Не считать месяц как последние 30 дней.
- Не принимать произвольный план уроков вне 6–10.
- Не удалять исторические оплаты при удалении ученика или группы.
- Не хранить данные банковских карт.
- Не добавлять онлайн-эквайринг без отдельного требования.
- Не публиковать `.env.local` или секреты Firebase в Git.
- Не ломать текущие календарные режимы и повторяющиеся серии.

Главная цель — сохранить удобный календарь и добавить прозрачный помесячный контроль: сколько уроков запланировано, сколько проведено, сколько должно быть оплачено и сколько уже оплачено.
